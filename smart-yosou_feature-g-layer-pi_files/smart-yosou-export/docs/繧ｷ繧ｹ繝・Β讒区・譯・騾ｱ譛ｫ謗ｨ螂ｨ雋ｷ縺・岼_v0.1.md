## 2. 構成要素

### 2.1 判定エンジンの呼び出し口 `scripts/judge.js`（新設・要アドendum）
- **役割**: 入力JSON（既存16キー＋任意 `odds_fuku`）を受け取り、`index.html` を jsdom で読み込んで `scoreHorse / calcArereScore / judgeConfidence / judgeKachiba / judgeQuadrant / buildBets` を**そのまま**呼び、判定と買い目をJSONで返す。
- **設計原則**: モジュール3の `buildBacktestRecord` と同じ方式（index.html の関数を jsdom 上で実行）。**ロジックの複製はゼロ**なので P3/P4 を満たす。
- 出力例:
  ```json
  { "race": "…", "arereScore": 58, "confidence": "mid", "quadrant": "📊 通常運用",
    "budgetTier": 500, "bets": [ {"type":"ワイドBOX","horses":[10,8,15,14],"points":6,"yen":600} ],
    "overhyped": [ … ], "pi_reference": [ … ]   // G層は参考欄のみ（P10）
  }
  ```
- 検証: `npm run check` に加え、同一JSONをブラウザで読み込んだ画面と `judge.js` の出力が一致することを jsdom テストで固定する。

### 2.2 J1：レース選定ジョブ（定時・木曜夜 or 金曜朝）
- 入力: プロジェクト知識（ARERU_RACES・運用フロー・戦略メモ）、Web検索で確認した**当週の開催日程**、月内予算消化額（`data/ledger.json` 想定）。
- 処理: 週末の重賞・OP から「荒れやすい条件（ARERU_RACES・ハンデ・小回り・道悪予報）」を優先して候補1〜2レースを選ぶ。日程は必ず検索し、**出典URLを添える**（P2）。
- 出力: `claude/weekly/YYYY-MM-DD_候補.md`（プロジェクト知識）＋通知。
  人はここで「承認／差替」するだけ。Perplexity情報を渡したい場合はこのメモに追記する（現行ステップ1の置き換え）。

### 2.3 人の手順（現行ステップ3）：スクショ投入
- 承認したレースの出馬表・血統・推定人気のスクショを**プロジェクトのファイルに追加**する（既存の png 群と同じ場所）。
- ファイル名規約を決める（例 `YYYYMMDD_レース名_出馬表_1.png`）。J2 はこの規約で当週分だけを拾う。
- 複勝オッズ（`odds_fuku`）が画面にあれば同じスクショに含める。無ければ J2 は「率のみ」表示で進む（P10）。

### 2.4 J2：判定・買い目ジョブ（定時・土/日 朝）
1. 当週規約のスクショを読み、**全頭JSON**を作成（下位人気も省略しない＝過去の失敗パターン対策）。
2. リポジトリ最新の `index.html` を取得し、`scripts/judge.js` で判定。
3. 判定が 🛑/🚫/⚠️ なら「見送り」を確定し、買い目は出さない（P3）。
4. 成果物を書く: `claude/weekly/YYYY-MM-DD_買い目.md`
   - 判定（荒れスコア・軸信頼度・総合判定・予算ティア）／買い目（券種・馬番・点数・金額）／過剰人気警告／JSON全文（ツールに貼れる形）／G層π参考欄（買い目非反映）。
5. 通知（プッシュ／メール）。人はメモを見て購入（P7）。判定に迷ったらタブレットで同じJSONをツールに貼れば**同じ結果**が出る（2.1の一致テストが担保）。

### 2.5 J3：結果記録・蓄積ジョブ（人の合図で起動）
- 起動: 人が結果スクショをプロジェクトに追加し、チャットで「結果記録」と言う（または手動起動）。
- 処理: 確定着順・確定馬場・払戻をスクショから読み取り（推測禁止・P6）→ J2 の JSON と突合 → `buildBacktestRecord` 相当のレコードを作成 → `data/samples/YYYY-MM-DD_レース.json` として保存 → `npm run backtest` を実行し結果を記録 → 収支台帳更新 → 連対種牡馬の F層追加は**提案としてメモ**（実装は別セッション）。
- push が必要（P9）。認可が無い間は、バンドル/パッチをチャットに出して人が取り込む。

### 2.6 保存場所の役割分担

| 場所 | 置くもの | 理由 |
|:--|:--|:--|
| プロジェクト知識（docs） | 週次メモ（候補・買い目・結果）、運用ルール、設計書 | 定時ジョブが毎回ゼロから読める唯一の共有記憶（P8） |
| プロジェクトのファイル | スクショ（入力・結果） | 現行運用と同じ。J2/J3 の入力元 |
| GitHub `smart-yosou` | `index.html`（正本）、`scripts/`、`data/samples/`、`data/ledger.json` | 判定コードとバックテスト資産。Pages で公開されるのは main のみ |
| 端末（タブレット） | ツール本体の閲覧・保存済みレース | 最終確認用。自動化後も従来どおり使える |

## 3. スケジュール案（JST）

| ジョブ | 起動 | 備考 |
|:--|:--|:--|
| J1 レース選定 | 木 21:00 | 週末の出馬確定前でも重賞は特定できる。金曜に人が承認 |

## 4. 安全策（判断を甘くしないための仕組み）

- **判定の一意性**: 買い目は `judge.js` 経由でしか生成しない。Claudeが文章で「私はこう思う」を買い目に混ぜない。異論があれば**別欄（所見）**に書く。
- **見送りの明示**: 🛑/🚫/⚠️ の週は「見送り」と理由を成果物の先頭に置く。買い目欄は空にする。
- **予算ガード**: `data/ledger.json` の月内消化額を J1/J2 が参照し、残額を超える提示をしない。
- **出典必須**: 日程・出走表に関する記述には検索の出典URLを付ける。付けられない情報は「未確認」と明記。
- **G層の隔離**: π参考値は成果物の末尾「参考（買い目非反映）」に固定。基準達成まで欄の位置を変えない（P10）。
- **失敗時の挙動**: スクショ不足・JSON不整合・`judge.js` エラーの場合は買い目を出さず「入力待ち／要確認」通知で止まる（推測で埋めない）。

- `data/samples/` に完全版レコードが **10レース以上**蓄積し、`npm run backtest` が結論を出せる状態になること。

- その上で、JRA公式データの自動取得（GitHub Actions）を別アドendumで設計する。
